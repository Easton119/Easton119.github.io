#### export_rkllm.py的作用
`export_rkllm.py` 其实串起了三件事（名字只取了最后一步）：

```python unfold
# ① 加载原始 HF 模型（fp16 权重）
ret = llm.load_huggingface(model=modelpath, ..., dtype="float16")   # 第 20 行

# ② 构建 + 量化（★量化在这里）
ret = llm.build(do_quantization=True,              # 第 40 行
                quantized_dtype="W8A8",            # 权重 int8 + 激活 int8
                quantized_algorithm="normal",
                target_platform="RK3588", ...)

# ③ 打包导出成 .rkllm 文件
ret = llm.export_rkllm("./..._W8A8_RK3588.rkllm")  # 第 47 行
```

- **`build()`** 才是真正做量化的地方：把 fp16 权重量化成 int8（W8A8），同时做算子/图优化，生成 NPU 能执行的中间表示。
- **`export_rkllm()`** 只是把量化好的模型打包成 `.rkllm` 文件，本身不做量化。

那 `generate_data_quant.py` 是干嘛的？
它是量化**之前**的准备工作，生成校准数据 `data_quant.json`：
- 用几条样本文本让 fp16 模型跑一遍，记录各层的激活值分布；
- `build()` 量化时读这个 `data_quant.json`，据此计算每层的量化参数（scale / zero-point），让 int8 量化精度损失更小。

所以完整链路是：
```text unfold
generate_data_quant.py（生成校准数据）
        ↓
export_rkllm.py → build()（用校准数据做真正的 W8A8 量化）
        ↓
export_rkllm()（打包导出 .rkllm）
```

## 完整部署流程（最终版）

> 最终跑通使用的版本是 RKLLM 1.3.1。整套流程横跨三台机器：Windows（中转/编辑）→ WSL（转换+交叉编译）→ RK3588 板子（推理）。

### 阶段 1：环境搭建（WSL）

```bash unfold
# 创建 conda 环境（Python 3.10，官方建议）
conda create -n rkllm python=3.10
conda activate rkllm
# 注意：rkllm_toolkit 的 whl 在 rknn-llm 仓库的 rkllm-toolkit/packages/ 目录里，
# 需先 clone 仓库（阶段 2）才能安装，具体命令见阶段 2 末尾
```

依赖里最重要的是 CUDA 版 PyTorch（量化要用 GPU）。本机 WSL 已直通显卡

| 转换环境 | 值 |
|---|---|
| GPU | NVIDIA RTX 4060 Laptop 8GB |
| torch | 2.6.0+cu124（CUDA 12.4） |
| 交叉编译链 | gcc-arm-10.3-2021.07-x86_64-aarch64-none-linux-gnu |

## 踩坑记录（按时间线）

### 坑 1：执行 export_rkllm.py 时 WSL 崩溃

**现象**：`python3 export_rkllm.py` 跑到一半，WSL 直接断开（VS Code 报 WebSocket 1006）。

**根因**：WSL2 默认只分配 8GB 内存（本机 16GB 的 50%）。float32 加载 1.5B 模型约 6GB，量化过程峰值远超，直接 OOM 崩。

**排查过程**：
1. 先改 float16（权重 6GB→3GB），以为能省内存 → 还是崩，因为量化峰值不止权重本身，还有 transformers 加载开销、量化中间张量、CPU↔GPU 搬运，8GB 仍不够。
2. 最终双管齐下：
   - `export_rkllm.py` 的 `dtype="float32"` 改 `"float16"`（省显存/内存）
   - 创建 Windows 侧 `C:\Users\qiyijin\.wslconfig` 加大内存：

```ini unfold
[wsl2]
memory=12GB
swap=8GB
```

   `wsl --shutdown` 重启后生效，内存从 7.6G 变成 11G。

### 坑 2（关键）：推理退化，刷`[PAD151935]`/ 刷数字"8"

现象：模型能加载、能推理、前半段答案正确，但生成到一半开始无限刷屏：

``` unfold
robot: 首先，设鸡的数量为x，兔子的数量为y。根据题目，我们知道总头数是1[PAD151935][PAD151935]...
robot: 兔的数量是（1888888888888888...
```

逐层排查（都没解决，最终定位到版本 bug）：

| 尝试                                                                         | 结论                                      |
| -------------------------------------------------------------------------- | --------------------------------------- |
| ① 以为是 float16 精度问题 → 改回 float32 重转                                         | 仍退化（排除 float16）                         |
| ② 改采样参数：`top_k=1→40`、`repeat_penalty→1.2`、`frequency/presence_penalty→0.6` | 仍退化（排除采样）                               |
| ③ 查 GitHub issue #424                                                      | 命中：这是 RKLLM 1.2.3 对 DeepSeek-R1 的量化 bug |

根因（官方 collaborator 确认）：issue #424 标题和现象完全一致——`[rkllm1.2.3]export deepseek-r1没有报错,但推理一直回答是[PAD151935]`。官方解释「这个模型对量化精度比较敏感」，即 RKLLM 1.2.3 的 W8A8 量化对 DeepSeek-R1-Distill-Qwen 有 bug，导致数值溢出、logits 算错、输出退化。

解决方案权衡：在降级和升级之间选择 升级 rkllm-toolkit 到 1.3.1

官方文档 `Rockchip_RKLLM_SDK_CN_1.3.1.pdf` 第 2.4 节明确要求 **NPU 驱动 ≥ v0.9.8**：

```bash unfold
# 板端查驱动版本
cat /sys/kernel/debug/rknpu/version
# RKNPU driver: v0.9.8   ← 刚好满足，无需重编内核
```

升级到 1.3.1（重装 toolkit、重新转换+编译+部署）后，退化问题消失，正常输出。

## 关键知识点

### build-linux.sh / CMakeLists.txt / llm_demo.cpp 三者的关系

| 文件 | 角色 |
|---|---|
| `src/llm_demo.cpp` | 源码：程序逻辑（加载模型、推理、输出） |
| `CMakeLists.txt` | 构建规则：声明「编哪个源文件、链哪个库、装到哪」 |
| `build-linux.sh` | 执行器：设置交叉编译链 → 调 cmake 读 CMakeLists → make 编译 → make install |

调用链：`build-linux.sh` 里设置 `GCC_COMPILER_PATH`（交叉编译链）→ `cmake ../..` 读取 `CMakeLists.txt` 生成 Makefile → `make -j4` 编译 `llm_demo.cpp` → `make install` 拷产物到 `install/`。

**为什么不能直接 `g++ llm_demo.cpp`**：① 交叉编译（WSL 是 x86_64，板子是 aarch64，得用 `aarch64-none-linux-gnu-g++`）；② 要链 `librkllmrt.so`、指定头文件 `rkllm.h` 路径；③ 参数太多，交给 cmake 管理更清晰。

**CMakeLists 里的相对路径坑**：`set(RKLLM_API_PATH "${CMAKE_SOURCE_DIR}/../../../rkllm-runtime/...")` 要求 `rkllm_api_demo` 待在 `examples/` 下、`rkllm-runtime` 在仓库根目录，**目录结构不能打散**，否则编译找不到头文件。

### ulimit 为什么需要

文件描述符统计的是「进程运行时打开的所有东西」，不是「目录里放了几个文件」。`llm_demo` 一跑起来就要打开：几十个依赖的动态库（libc/libm/libstdc++ 等）、NPU 设备节点、模型内部的多个映射。默认上限 1024，大模型加载可能超限报 `Too many open files`，所以 `ulimit -HSn 102400`。

### 参数 2048/4096 的含义

`llm_demo.cpp` 源码第 75 行明确写 `Usage: model_path max_new_tokens max_context_len`，第 94-95 行：

```cpp unfold
param.max_new_tokens = std::atoi(argv[2]);   // 参数2 = 2048 = 最大生成长度
param.max_context_len = std::atoi(argv[3]);  // 参数3 = 4096 = 最大上下文长度
```

所以 `./llm_demo xxx.rkllm 2048 4096` 里 **2048 是 max_new_tokens（单次最多生成）、4096 是 max_context_len（上下文总容量）**——上下文 > 生成长度，才合理。课件 PDF 把两个参数的解释写反了。

### 贪心解码（top_k=1）与退化

`llm_demo.cpp` 默认 `top_k=1` 是贪心解码：每次都只选概率最高的那一个 token，零随机性。一旦某步选错就一路错到底。量化模型（W8A8）的 logits 有误差，某些位置「概率最高 token」会算歪，贪心解码就会陷入重复循环（刷同一个 token）。这是量化 + 贪心解码的固有风险，通过加大 `top_k`（引入采样随机性）、`repeat_penalty`/`presence_penalty`（惩罚重复）可以缓解——但本次的根因是 1.2.3 的量化 bug，调采样参数无效，升级版本才是对症下药。
