传统 DCMI 与 STM32N6 DCMIPP 的本质区别：

  • 输入方式：DCMI 仅支持传统并行接口（D0~D13 + PIXCLK/HSYNC/VSYNC）；DCMIPP 原生支持 MIPI CSI-2 串行差分总线。
  • 处理能力：DCMI 无法处理 RAW 数据，无缩放和裁剪引擎，只能单纯将像素搬入 RAM；DCMIPP 内置完整硬件 ISP，拥有硬件级 Decimation 抽取、Downsize 分数缩放以及 PixelPacker 打包引擎。
  • 通道架构：DCMI 通常为单数据流通道；DCMIPP 支持多个并行处理 PIPE，可实现单传感器输入、多尺寸异步输出。

二、从物理光信号到 RGB888 的 7 步蜕变

IMX335 输出的 RAW10 并非可直接查看的彩色位图，而是覆盖着拜耳滤光阵列（Bayer Color Filter Array, CFA）的感光原数据：

       Bayer 滤光阵列排列特征 (每个像素仅感应一种基色)
                  [ R ]  [ Gr ]  [ R ]  [ Gr ]
                  [ Gb ] [ B ]   [ Gb ] [ B ]
                  [ R ]  [ Gr ]  [ R ]  [ Gr ]

三、图像取景、裁剪与下采样数学原理

传感器原生分辨率为 2592×1944 (4:3)，总像素达 5,038,8485,038,8485,038,848（约 500 万像素）。系统最终要求 PIPE1 输出 800×480 (5:3) 显示图像，PIPE2 输出 128×76 神经网络检测图像。

1. 为什么不直接在内存中保存 2592×1944 RGB888 图像？

  1. 显存超限：单帧 2592×1944×3 字节 =15,116,544 B≈14.4 MiB= 15,116,544 \text{ B} \approx 14.4 \text{ MiB}=15,116,544 B≈14.4 MiB。为防止画面撕裂需采用 4 缓冲机制，仅背景层就需要消耗 ≈57.7 MiB\approx 57.7 \text{ MiB}≈57.7 MiB，直接击穿板载分配给 .EXTRAM 的 16 MB PSRAM 物理边界（STM32N647X0HXQ_LRUN_RAMxspi1.ld:48）。
  2. 总线与算力浪费：LTDC 显示屏幕的物理点阵仅为 800×480（bsp_lcd.h:27-28）；后级神经网络输入更只有 128×128 与 192×192。高分辨率在没有硬件直通缩放的前提下毫无意义。

2. Manual ROI 视角自适应裁剪推导

LCD 屏幕宽高比为 800:480=5:3800:480 = 5:3800:480=5:3（约为 1.667），而传感器为 2592:1944=4:32592:1944 = 4:32592:1944=4:3（约为 1.333）。若直接强行缩放会导致画面严重拉伸变形。系统在 app_camera.c:130-144 采用了最大等比内接居中裁剪策略：

四、DCMIPP 两级硬件缩放原理及定点数数学实现

从 2592×1555 的截取画面缩放至各个 PIPE，由 DCMIPP 内部的 Decimation（整数粗抽取） 和 Downsize（分数细缩放） 级联完成。

1. 为什么采用两级缩放策略？

DCMIPP 的缩放由两个物理硬件块组成，能力互补：

  • Decimation 粗调：仅支持硬性的 ×1\times 1×1、×1/2\times 1/2×1/2、×1/4\times 1/4×1/4、×1/8\times 1/8×1/8 降采样跳步，负责在超大比例缩放时迅速减轻总线压力；
  • Downsize 细调：支持高精度分数缩放比（以 8192 代表 1.0×1.0\times1.0×，最大支持约 8.0×8.0\times8.0× 缩放）。

因此代码（cmw_utils.c:125-135）的通用控制逻辑是：先把比例压到 8 以内，再交给 Downsize 做精细缩放。

【通俗透彻解读】Downsize 的神秘数字到底怎么来的？

看似复杂的 8192、26542、316，核心其实只有两句话：

  1. 硬件不会算带小数点的数（浮点数太慢），所以要把 3.24 放大成整数。
  2. 硬件极其讨厌算除法（除法太耗时），所以提前把“除法”算成“乘法”。

通俗解读 1：为什么会有 8192？——“元换成分”的把戏

  • 生活例子（记账不用小数）： 假设你要记录 3.24 元，但系统只允许存整数、不能有小数点，你会怎么做？

    把单位改成“分”：3.24×100=3243.24 \times 100 = 3243.24×100=324 分。全存整数，用的时候心里清楚除以 100 就行。

  • 硬件原理（不用 100，用 8192）： 计算机是二进制的，对它来说乘以或除以 2 的次方（如 2、4、8、16…8192）根本不需要计算，只需要把二进制位往左或往右挪一挪（移位操作），一个时钟周期搞定，几乎零开销。 硬件设计者选了 819281928192（即 2132^{13}213） 作为放大的基准（相当于二进制里的“100 分”）：
    • 放大 1.0 倍（原图不动）：1.0×8192=81921.0 \times 8192 = \mathbf{8192}1.0×8192=8192
    • 放大 2.0 倍：2.0×8192=163842.0 \times 8192 = \mathbf{16384}2.0×8192=16384
    • 缩小的 3.24 倍：3.24×8192=265423.24 \times 8192 = \mathbf{26542}3.24×8192=26542
    /* cmw_utils.c:99 */
down->HRatio = (uint32_t)(8192 * ratio_width); // 8192 * 3.24 = 26542

    通俗结论：HRatio = 26542 根本不是什么神秘数字，它就是 “3.24 放大 8192 倍后的整数”。

通俗解读 2：为什么还要搞出 HDivFactor = 316？——“除法变乘法”

  • 生活例子（超市打折心算）： 如果一件商品要除以 4，你在心里可能不会做除法，而是心算：

    乘以 0.25。因为 A÷4=A×0.25A \div 4 = A \times 0.25A÷4=A×0.25。

  • 硬件原理（提前把除法算好）： 在流水线里每个像素都要算一次位置，如果每个像素都去算一次除以 3.24，流水线直接卡死。硬件工程师的做法是：初始化时，先把 1÷3.241 \div 3.241÷3.24 算好，流水线运行时直接做乘法。 怎么把 1÷3.241 \div 3.241÷3.24 变成整数？

    13.24=8002592≈0.30864\frac{1}{3.24} = \frac{800}{2592} \approx 0.30864 3.241​=2592800​≈0.30864

    不能存小数 0.30864，硬件选择把这个数放大 1024 倍（即 2102^{10}210）：

    0.30864×1024≈3160.30864 \times 1024 \approx \mathbf{316} 0.30864×1024≈316

    代码里为了避免浮点计算，直接用纯整数形式写成了：
    /* cmw_utils.c:101 */
down->HDivFactor = (1024 * 8192 - 1) / down->HRatio;
// (8388607) / 26542 ≈ 316

    通俗结论：HDivFactor = 316 就是 “倒数 13.24\frac{1}{3.24}3.241​ 放大 1024 倍后的整数”。有了这个数，硬件在反向找像素时，只要做 × 316 再右移 10 位，根本不需要做除法。

通俗解读 3：Bresenham 累加器跑道插旗比喻

想象一条 2592 米长的跑道（原始图像宽度），你想在上面均匀插 800 根旗子（缩放后的宽度）。

  1. 每两根旗子之间的距离是：2592÷800=3.24 米2592 \div 800 = 3.24 \text{ 米}2592÷800=3.24 米。
  2. 机器人要一步一步走，每步走 3.24 米插一根旗。
  3. 但机器人的计数器只能认整数步数，它把 1 米细分成 8192 个微步。
  4. 那么每走一根旗的距离，就是：3.24×8192=26542 个微步3.24 \times 8192 = 26542 \text{ 个微步}3.24×8192=26542 个微步，这就是 HRatio = 26542。
  5. 机器人每次累加 26542 个微步，满 8192 就向前跨一个原始像素，这就是硬件缩放引擎内部的累加器工作方式（Bresenham 算法）。

缩放处理完成后，数据流进入 PixelPacker 阶段，由专用 DMA 写入 RAM。

DCMIPP 缩放后内部像素流
         │
         ▼

         ▼

【通俗透彻解读】像素打包、Pitch、16 字节对齐与 DMA

1. 什么是“打包”（PixelPacker）？

  • 技术含义：前面 ISP 处理完的像素点，在硬件芯片内部可能还是浮点或宽位数的电信号。PixelPacker（像素打包器） 负责把它们按工业标准拼装好。配置成 RGB888，就是让它每 1 个像素占用 3 个字节（R 占 1 字节、G 占 1 字节、B 占 1 字节）。

2. 算式 800 × 3 = 2400 在算什么？—— 什么是“Pitch”（跨距/步长）？

  • 生活例子（方格纸写字）： 假设你有一张方格作文纸，一行能写 800 个字。每个字要用彩色荧光笔涂满 3 个小格子（RGB 各占一格）。那你写完完整的一行，一共占了多少个小格子？

    一行占的格子数=800 个字×3 格/字=2400 格\text{一行占的格子数} = 800 \text{ 个字} \times 3 \text{ 格/字} = 2400 \text{ 格} 一行占的格子数=800 个字×3 格/字=2400 格

    写下一行时，你的笔尖必须跳过这 2400 格，从第 2401 格开始写。
  • 技术含义（Pitch）： 图像在内存里其实不是二维的面，而是一根极其漫长的一维单行线。硬件要想在一维内存里存一张 800×480 的图片，必须知道存完第 1 行像素后，要跨过多少个字节才能到第 2 行的开头。这个“跨过去”的距离，硬件术语叫 Pitch（行跨距/步长）。
    /* cmw_camera.c:1254 */
pipe_conf.PixelPipePitch = p_conf->output_width * p_conf->output_bpp;
// output_width = 800 (宽度800像素)
// output_bpp   = 3   (RGB888格式每像素3字节)
// 800 * 3 = 2400 字节

3. “16 字节对齐”与算式 (Pitch + 15) & ~15 是什么意思？

  • 生活例子（仓库叉车整箱搬运）： 仓库叉车有个死规定：每次搬运必须是 16 箱的整倍数，不够 16 箱也得补齐凑满整箱，否则叉车卡槽对不齐不给搬。如果某一行算出来是 2401 字节，不是 16 的倍数，叉车就不干了，必须补齐（Padding）到 2416 字节。
  • 源码的位运算写法：
    /* cmw_camera.c:1256 */
pipe_conf.PixelPipePitch = (pipe_conf.PixelPipePitch + 15) & (uint32_t) ~15;
    这是嵌入式里最经典的向上取 16 整倍数的极速算法。我们的一行正好是 240024002400 字节，算一下：

    2400÷16=150(正好整除，没有任何余数！)2400 \div 16 = 150 \quad (\text{正好整除，没有任何余数！}) 2400÷16=150(正好整除，没有任何余数！)

    所以经过这一行运算后，数值依然是 2400，不需要浪费多余空间做无用填充。

4. DMA 搬运的“具体内容与终点”是谁？

  • 什么是 DMA（总经理与搬运工）： CPU 是总经理，每天要处理核心算法（算 AI 模型、判断睁闭眼、跑操作系统）。DMA（直接内存访问）就是专职搬运工。总经理（CPU）只需要在开机时交代一句：“你听着，摄像头处理好的画面，你自动给我原封不动搬到内存地址 A，填满一帧就喊我一声”。之后整个数据传输完全不占用 CPU 一丁点算力，是纯硬件在后台默默倒腾数据。
  • 搬运内容大小：

    单帧字节数=800×480×3 字节=1,152,000 字节≈1.15 MB\text{单帧字节数} = 800 \times 480 \times 3 \text{ 字节} = 1,152,000 \text{ 字节} \approx 1.15 \text{ MB} 单帧字节数=800×480×3 字节=1,152,000 字节≈1.15 MB

  • 搬运的终点目的地： app_lcd_bg_buffer（背景帧缓冲区）。在代码里，它是一个分配在外部高速内存（PSRAM）里的大数组：
    /* app_lcd.c:26 */
static uint8_t app_lcd_bg_buffer[DISPLAY_BUFFER_NB][LCD_BG_WIDTH * LCD_BG_HEIGHT * 3] 
               __attribute__((aligned(32))) __attribute__((section(".EXTRAM")));
    一共有 DISPLAY_BUFFER_NB = 4 张这样的大图轮流倒腾（四缓冲乒乓机制）。
  • 搬运指令在哪下的： 每次相机开工或一帧拍完时，CPU 通过这一行告诉硬件 DMA 目标地址：
    /* app_camera.c:80 */
HAL_DCMIPP_PIPE_SetMemoryAddress(CMW_CAMERA_GetDCMIPPHandle(), DCMIPP_PIPE1, 
                                 DCMIPP_MEMORY_ADDRESS_0, (uint32_t)display_pipe_destination);
    只要这一行地址一设，DMA 硬件就像开闸放水一样，把 1,152,000 字节的彩色像素直接灌进 app_lcd_bg_buffer 里。

六、内存数据下游消费与红蓝通道（Swap）策略

当 1,152,000 字节完整载入 app_lcd_bg_buffer 后，触发帧完成中断，数据将分流至两个下游消费者：

                    ┌──► [ LTDC 屏幕控制器 ] ──► 刷屏至 800×480 物理液晶屏 (实时背景)
                    │
[ 1.15 MB 帧缓冲 ] ─┤
                    │
                    └──► [ CPU 关键点预处理 ] ──► 扣取人脸 ROI，缩放到 192×192
                                                  送给 468 点网络进行眼睑状态判别
  1. LCD 显示控制器（LTDC 硬件）：直接从这块内存读数据，通过显示线刷到 800×480 的液晶屏上，提供实时流畅背景。
  2. AI 关键点算法（CPU 软件）：在 app_face_landmark_run() 里，CPU 按照检测到的人脸框位置，直接钻进这块内存里把脸部那一小块矩形区域抠出来，软件双线性缩放到 192×192 送给 468 点关键点网络去预测眼睛轮廓。

PIPE1 与 PIPE2 红蓝通道翻转（enable_swap）的底层原因

在 app_camera.c 初始化中，存在一处显著差异：

  • PIPE1 (显示管线)：enable_swap = 0
  • PIPE2 (神经网络管线)：enable_swap = 1

该功能映射到硬件寄存器 P1PPCR_SWAPRB 与 P2PPCR_SWAPRB（stm32n6xx_hal_dcmipp.c:6469/6473），由于其工作在 PixelPacker 内部，因此各管线可完全解耦：

  1. PIPE1 直通：ISP 输出的标准字节序为原生的 R、G、B 排列，正向送入屏幕控制器 LTDC，确保显示画面的肤色自然准确。
  2. PIPE2 互换：BlazeFace 预训练权重基于特定通道顺序（BGR/RGB 适配），硬件层激活 enable_swap=1 会在 DMA 搬运前将高低字节位置交换。利用片上硬件完成红蓝通道翻转，规避了在 CPU 中遍历数组进行字节调换的高昂运算开销。
